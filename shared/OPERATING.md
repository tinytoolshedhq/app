# Bot 協作規範

## 必須遵守
1. 使用者可直接向任何職責相符的 bot 交辦，不設主要對話 bot。
2. Bot 之間的任務、問題與結果一律透過本 repo 的檔案交接。不得直接向其他 bot 傳送任務內容或進行來回討論。
3. 交辦時，在 `shared/tasks/<收件 bot>/inbox/` 新增一份任務檔；只寫目標、必要背景、相關檔案及完成條件。不要複製整段聊天紀錄。
4. 收件 bot 只讀指定任務及完成工作所需的檔案或差異，不要預設掃描整個 repo、其他 bot 的 inbox 或歷史任務。
5. 結果寫入 `shared/results/<任務檔名>`，包含結論、產出位置及需要使用者決定的事項。完成後將任務移至該 bot 的 `done/`。需要其他 bot 接手時，另寫一份任務並引用結果檔，不直接傳訊息。
6. 自動喚醒只傳任務路徑與版本資訊，不帶整份文件或聊天紀錄。不用模型定時詢問是否有新任務。若未接好自動觸發，由使用者提供任務路徑啟動。
7. `shared/` 的純文件與交接檔直接 push 到 main，不開 PR。程式碼變更仍遵守各專案規範。
8. 不將密鑰、登入憑證或 webhook secret 寫入 repo。公開發文等操作仍遵守原有的使用者授權條件。

## 任務主責與交接時機
- 每個任務由一個 bot 主責，負責整合產出、確認完成條件並向使用者回報；不設所有任務共用的主要對話 bot。
- 主責 bot 自行完成其能力與授權範圍內的工作。只有缺少必要的專業能力、工具或帳號權限，或任務需要獨立審查時，才建立跨 bot 任務。
- 不為轉述、確認收到、詢問一般進度或重複規劃而喚醒其他 bot。協調 bot 不作為所有任務的必經入口。
- 委派一部分工作時，原主責 bot 繼續負責整體任務；子任務須記載原主責與原任務路徑。移交整體責任時，明確記載接任主責與剩餘工作。
- 對方的任務檔須說明交接原因與具體產出。保留必要的獨立審查，不以減少交接為由省略。

## 精簡但完整的上下文
- 任務提供目標、已確認的事實與決定、本次變更、必要來源、完成條件及尚待決定的事項，讓收件 bot 能直接開工。寫法見 `shared/tasks/README.md`，不做格式驗證。
- 穩定的產品事實、品牌語氣與地區規則按主題放在 `shared/context/`；任務引用相關檔案、版本與段落，不複製全文或聊天歷史。
- 收件 bot 先讀任務及指定段落，資訊不足時再擴大搜尋。不要為了省字省略必要證據；數字、期限、版本、授權條件與不確定事項必須準確保留。
- 結果只記錄結論、證據或修改位置、未解決事項與下一步責任人。詳細操作紀錄按需另存檔，不逐輪轉述。
- 委派結果寫回 repo 後不以直接訊息通知。主責 bot 正在執行時按需讀取；已停止且確需整合時，另建一份引用結果的續辦任務，不用模型輪詢。

## 職責
- 可憐的碼農：程式修改、PR、Expo/EAS builds。
- 亞洲小編／美洲小編／歐洲小編：各自負責的發文、回覆及已登入帳號操作。
- 黑麻麻：確有跨 bot 協調需求時，透過上述任務檔流程協調。
- 其他 bot：只處理各自職責內的任務。
- 胖嘟嘟阿姨、漏洞大師：預定移除，不再建立新任務或審核依賴。此文件不會刪除平台上的 bot。

## 共享位置
- 本 repo `shared/`：短期任務、草稿、排程與結果。
- `tinytoolshedhq/tinytoolshed-backup/shared/`：長期策略及筆記。只在任務需要時讀取；本次未同步修改該 repo。

## 啟動設定
每個 bot 的常駐指令與 routine 指令都應加入：

> 開始處理 repo 工作前，讀取目前版本的 shared/OPERATING.md 並遵守。每個任務由一個 bot 主責；能力或權限不足、需要獨立審查時才交接，協調 bot 不是必經入口。Bot 之間只透過 shared/tasks/ 與 shared/results/ 交接，不直接傳訊息。交接保留必要事實、決定、變更、來源、完成條件與授權；收到任務後只讀必要引用，缺少資訊再擴大搜尋。結果寫回 repo，不向其他 bot 輪詢或發送收到／進度通知。

## 實作狀態
本文件是協作約定，不能自行限制平台上的工具、權限或通訊方式。
Repo 由 `.github/workflows/bot-handoff.yml` 監聽任務變更；實際喚醒需完成 Grok routine、GitHub secret 設定，並將 `BOT_HANDOFF_ENABLED` 設為 `true`。停用或手動執行時只預演，不呼叫 bot。
任務目錄使用方式及觸發範圍見 `shared/tasks/README.md`。
